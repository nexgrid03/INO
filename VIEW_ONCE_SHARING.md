# INO — View Once Document Sharing

A one-time, self-destructing share. The recipient can open the document
**exactly once**; after the first successful open the link is permanently dead.

This is **additive**. `document_shares`, the `create_document_share` RPC, the
existing QR/link flow, the Vercel `/s/<token>` viewer and every auth path are
untouched — normal sharing behaves byte-for-byte as before.

```
Owner: select ONE document → Share → mode: View Once → link/QR
                                      https://share.inoapp.in/v/<token>

Recipient opens link →  ┌─ gate: "opens only once — open it?"   (burns nothing)
                        └─ presses Open once → token BURNED → document shown
Anyone opens it again → "This document has already been viewed or has expired."
```

---

## 1. The one-time guarantee

The gate is a **single atomic SQL statement**, not application logic:

```sql
update public.view_once_shares s
   set viewed = true, viewed_at = now(),
       access_key = <fresh uuid>, access_expires_at = now() + interval '5 minutes'
 where s.token = p_token
   and s.viewed = false          -- ← the whole guarantee
   and s.revoked = false
   and s.expiry_time > now()
returning *;
```

Two concurrent opens cannot both succeed: Postgres locks the row, the loser's
`WHERE` no longer matches, and it is told the link is spent. No read-then-write
race exists because there is no separate read.

### Why claiming is a separate, explicit step

Loading the recipient page **must not** spend the view. If it did, a WhatsApp or
Slack link-preview crawler, a page refresh, a mis-tap on a notification, or an
`initState` retry would silently destroy the share before a human ever saw it.

So there are two endpoints:

| Endpoint | Method | Burns the link? |
|---|---|---|
| `GET  /share/v/<token>` | GET | **No** — non-consuming status peek |
| `POST /share/v/<token>/claim` | POST | **Yes** — atomic, exactly once |
| `GET  /share/v/<token>/file?k=<key>` | GET | No — needs the claim's key |

Claiming is POST-only on purpose: no crawler, prefetch or accidental navigation
can consume a one-time link.

### Why there is an access key

Marking `viewed = true` and *then* trying to fetch the bytes would lock the one
legitimate viewer out of the document it just earned. So the same atomic UPDATE
mints a short-lived `access_key` (5 minutes) and returns it to that single
caller. The file endpoint accepts the key, not the token.

## 2. Schema

`supabase/migrations/20260735000000_view_once_shares.sql`

| Column | Purpose |
|---|---|
| `token` | 32-hex public handle (`gen_random_uuid()` minus dashes, ≈122 bits). **Generated by Postgres, never the client** |
| `document_id` | FK to an **existing** `documents` row — storage is reused, nothing is copied |
| `owner_id` | FK to `auth.users`, defaults to `auth.uid()` |
| `expiry_time` | Optional expiry: the link can lapse before it is ever opened |
| `viewed` / `viewed_at` | The one-time flag. Set once, never unset |
| `revoked` | The sender can kill a link before it is opened |
| `access_key` / `access_expires_at` | The short-lived post-claim grant (see above) |
| `viewer_ip_hash` | SHA-256 of the opener's IP — forensics without storing a raw address |

**RLS:** owner-only select/insert/update/delete. There is deliberately **no anon
policy** — anonymous recipients never touch the table.

**Functions and who may call them:**

| Function | Granted to | Notes |
|---|---|---|
| `create_view_once_share(document_id, ttl_seconds)` | `authenticated` | Verifies the document belongs to the caller |
| `peek_view_once_share(token)` | `service_role` | Non-consuming status |
| `claim_view_once_share(token, ip_hash)` | `service_role` | The atomic gate |
| `resolve_view_once_file(token, access_key)` | `service_role` | Returns the storage path — server-side only |
| `purge_expired_view_once_shares()` | `service_role` | Optional cron housekeeping |

`EXECUTE` is revoked from `PUBLIC` on all five first, so anon and signed-in
clients cannot reach the one-time gate directly.

## 3. Security properties

- **No direct storage URLs, ever.** The Edge Function mints a 60-second signed
  URL server-side, fetches the object itself and streams the bytes back. The
  client never sees the bucket path, the signed URL, the owner or the document
  UUID.
- **Random UUID tokens, minted by Postgres.** The client cannot forge or
  predict one.
- **Token reuse is impossible** — the atomic UPDATE, above.
- **Optional expiry** — 10 minutes / 1 hour / 24 hours / 7 days.
- **Uniform terminal responses.** `viewed`, `expired` and `not_found` all render
  the same message to the recipient, so probing a token can't reveal whether it
  ever existed.
- **Inline only.** There is no `mode=download` for a view-once document; the
  Edge Function always serves `Content-Disposition: inline` with `no-store`.
- **Ownership re-checked on every path.** The document must still belong to the
  link's owner at peek, claim and file time.

## 4. Screenshot protection

Implemented as a small MethodChannel (`ino/secure_screen`) against code already
in `MainActivity.kt` / `AppDelegate.swift` — **no new pub dependency**, which
matters given this project's pinned AGP 9 toolchain.

`lib/services/screen_security_service.dart` reference-counts holders, so a
nested push/pop can't lift protection while an outer secure screen is still up.

### Android — real protection

`enable()` sets `WindowManager.LayoutParams.FLAG_SECURE` on the activity window.
The OS then:

- refuses screenshots outright,
- blanks the window in screen recordings,
- blanks the recents/task thumbnail,
- blocks mirroring to non-secure displays.

This is enforced by the system, not the app. It is scoped to the view-once
viewer only — the rest of the app is unchanged.

### iOS — the honest limitation

**iOS provides no public API to block screenshots.** There is no counterpart to
`FLAG_SECURE`; anything claiming otherwise relies on private API (App Store
rejection) or on tricks that break across iOS releases. INO does not pretend
otherwise — the recipient is told this in plain words on the gate screen.

What is implemented instead is everything iOS genuinely allows:

1. **App-switcher privacy** — an opaque cover is placed over the window on
   `willResignActive`, so the document never appears in the multitasking
   snapshot (the one capture iOS performs on its own).
2. **Screen-recording / AirPlay-mirroring detection** — `UIScreen.isCaptured` is
   observed live via `capturedDidChangeNotification`; while capture is active the
   Flutter viewer **hides the document** behind a notice.
3. **Screenshot detection** — `userDidTakeScreenshotNotification` is reported to
   Flutter after the fact, and the viewer shows a banner.

The real guarantee on iOS is the one-time token: a screenshot only ever captures
a document the recipient was already authorised to see once, and the link is
already permanently dead by the time the document is on screen.

### Web

A browser cannot block screenshots either. The web viewer disables right-click
and text selection as deterrents (and says so in the code), warns before
unloading, and relies on the one-time token for the actual guarantee.

## 5. Rendering the document

| File kind | In the INO app | In the web viewer |
|---|---|---|
| Image | `Image.memory` — bytes stay in RAM, never written to disk | inline, pinch-zoom |
| PDF | no in-app renderer exists in this project; offered via the system viewer behind an explicit warning, and the temp file is deleted on return | inline via `react-pdf` |
| Other | same as PDF | "can't be previewed" (no download fallback — the contract is *view*) |

The PDF-in-app gap is the one honest rough edge: INO has no PDF rendering
dependency, so a PDF has to be handed to the device's viewer, where screenshot
protection no longer applies. The recipient is told this before it happens, and
the file is wiped as soon as they come back. Adding `pdfx` or
`syncfusion_flutter_pdfviewer` would close it — deliberately not done here, since
it changes the build graph.

## 7. Deployment

1. **Database** — `supabase db push` (or paste
   `20260735000000_view_once_shares.sql` into the SQL editor; it is idempotent
   and ends with `notify pgrst, 'reload schema'`).
2. **Edge Function** — `supabase functions deploy share --no-verify-jwt`.
3. **Web frontend** — redeploy `share-frontend/` to Vercel. The `/v/<token>`
   route ships with it; no new environment variables.
4. **App** — rebuild. The MethodChannel needs the native changes, so a hot
   reload is not enough.

Optional: schedule `select public.purge_expired_view_once_shares();` daily to
clear spent access keys and drop rows dead for 30+ days.

### Verifying it works

```bash
# 1. Peek — must NOT burn the link. Run it twice; both say "ready".
curl -s "$FN/share/v/<token>?format=json"

# 2. Claim — burns it. Returns accessKey.
curl -s -X POST "$FN/share/v/<token>/claim"

# 3. Claim again — must be refused with 410.
curl -s -i -X POST "$FN/share/v/<token>/claim"

# 4. Bytes, with the key from step 2.
curl -s -o out.bin "$FN/share/v/<token>/file?k=<accessKey>"

# 5. GET on /claim must be rejected (405) - a GET can never destroy a share.
curl -s -i "$FN/share/v/<token>/claim"
```

## 8. What this feature deliberately does not do

- **It does not stop a recipient photographing the screen with another phone.**
  Nothing can. The one-time token limits *how many times* a document can be
  retrieved, not what a determined viewer does with the pixels.
- **It does not block iOS screenshots** — see above.
- **It does not duplicate files.** A one-time link points at the document already
  in Storage. Revoking or expiring a link never touches the original.
- **It does not change normal sharing.** Every existing path — processed copies,
  multi-document shares, the `/s/` viewer, revocation, analytics — is exactly as
  it was.
